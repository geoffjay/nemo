# Knowledge Base Update Log

## 2026-07-15
* **Feature**: Made the theme selectable and savable from the settings view (`ctrl+p`). Split the settings sidebar into a **Global** page (persists to `~/.config/nemo/config.toml` via `NemoConfig::save()`) and a **Project** page (persists to the loaded `app.xml`), each with a theme-set dropdown and a color-mode dropdown built from `gpui_component::DropdownButton` + `PopupMenuItem::on_click` (whose `&mut App` is exactly what `theme::apply_configured_theme` takes, so selection applies live and saves in one closure). The theme dropdown lists the 7 theme *sets* via the new `theme::get_theme_set_names()`; mode stays a separate control. Project edits are written back to `app.xml` by the new `workspace::xml_edit::set_app_theme` — a surgical text edit that updates only the `<theme>` element's `name`/`mode` attributes (or inserts one under `<app>`), preserving the rest of the hand-authored file (6 unit tests). Added `AppConfig.theme_mode: Option<String>` (honored at startup in `main.rs`) and `NemoRuntime::config_path()`. The project layer still overrides global on load, so a saved project theme takes precedence; default behavior (no theme anywhere → gpui default) is unchanged. Deferred: an `overrides.xml` overlay to keep `app.xml` immutable. Updated [configuration](/docs/knowledgebase/concepts/configuration.md) with the two-layer persistence model.
* **Plan**: Researched runtime component creation viability and added plan [runtime component creation](/docs/knowledgebase/plans/runtime-component-creation.md). Finding: the component system is closed at the render layer (monolithic `match` in `app.rs:render_component`, no trait/callback/registry lookup) but open by design at the registry layer (`ComponentFactory` trait and `DescriptorSource::Plugin` exist as dead code; `PluginInitResult.components` is silently dropped by `ExtensionManager::init_plugins`). The plan targets Layer 1 only — runtime insert/remove of *built-in* component instances via Rhai and `PluginContext` (static props, no `<binding>` support, full create+remove lifecycle). It's viable because `BuiltComponent` is a flat ID-keyed `HashMap<String, Value>`, `LayoutManager` is already `Arc<RwLock>` mutated incrementally, render snapshots before rendering, and state is lazy/ID-keyed. Layers 2 (plugin-declared types via declarative render callbacks) and 3 (native custom-rendering ABI) recorded as future work.
* **Feature/Fix**: Reworked the task-list example into a genuinely dynamic, JSON-backed todo app and added the two framework capabilities it needed. (1) **On-load hook**: `<script on-load="fn" />` runs a handler once after the layout is built (`NemoRuntime::on_load_handler` → `App::new`, called as `fn("app","load")`). This is the fix for the "check one → top three check" bug — the old script deferred applying persisted state onto the first click (there was no startup hook), so saved `done` states appeared all at once on first interaction; now the table is hydrated before the first paint. (2) **Input value readback**: an `<input>`'s typed text is synced into its `value` property on change/blur (Enter fires `on-change`), so `get_component_property(id,"value")` returns live text, and the render pass pushes script-set `value` back into the field (e.g. clearing after submit) without fighting the cursor — see `App::get_or_create_input_state`/`sync_input_value`. The example now starts empty (no defaults baked into XML), creates `tasks.json` if missing, adds tasks via a modal, renders into a data-driven `<table>` (text-only cells — "done" is a ✓ glyph, toggle/delete keyed by the row number), and writes every change to disk. Rewrote `test_task_list_handlers_end_to_end` for the new lifecycle; added parser tests (`test_parse_scripts_with_on_load`, `…_without_on_load_omits_key`) and runtime tests (`test_on_load_handler_reads_config`, `…_absent_is_none`). Updated [extensions](/docs/knowledgebase/concepts/extensions.md) and the example README. Note: `on-load`/attribute keys are kebab→snake normalized at parse time, so read them as `on_load`.
* **Fix**: The dev-dashboard "Refresh All" didn't update the System Info panel. `refresh_sys` calls `cmd(...)` (rhai-process), which is opt-in and absent from the default build (default = pkg-env + pkg-sci), so `cmd` threw `Function not found` and aborted the whole `refresh_all` handler (via `ensure_init`). Wrapped each command in Rhai `try`/`catch` so a missing package degrades to an "unavailable — rebuild with --features pkg-process" message and the other panels still refresh. Extracting the disk-summary loop into a `disk_summary` helper kept the try block shallow — deep nesting inside a try block tripped Rhai's expression-complexity limit. Added `test_dev_dashboard_refresh_all_runtime` (asserts a real `uname` result with pkg-process) and `test_dev_dashboard_refresh_all_degrades_without_process` (asserts graceful degradation without it).
* **Fix**: Id-less ("anonymous") components in different parents collided, so e.g. every prefix `<label>` in the dev-dashboard rendered the last one's text ("all labels show Median:"). Cause: `children_to_component_map` (`xml_parser.rs`) numbered anonymous ids with a counter that reset per parent, so the first id-less child of every parent became `__anon_1`; since `LayoutManager` flattens components into an id-keyed map, they collapsed to one entry. Fixed by making the counter document-global (a `Cell<usize>` on `XmlParser`, reset per `parse()`). Added `test_anonymous_components_get_document_unique_ids` (parser) and `test_anonymous_labels_survive_full_build_pipeline` (full build). Documented the "IDs must be unique document-wide" invariant in [configuration](/docs/knowledgebase/concepts/configuration.md).
* **Fix**: Rhai handler scripts with top-level `let`/`const` declarations (like the task-list example's `tasks_loaded` flag) failed with "Variable not found" on every UI interaction. Root cause: `RhaiEngine::call` used an empty `Scope::new()` clone, so `call_fn` never saw module-level variables. `load_script` now runs the script's top-level statements once against a persistent `Scope` to seed module state, and `call` reuses (and mutates) that scope across invocations so variables survive. `call`/`call_script` take `&mut self`; the runtime's `call_handler` takes the extension manager write lock. Added a regression test (`test_module_state_persists_across_calls`). Updated [extensions](/docs/knowledgebase/concepts/extensions.md).
* **Fix**: The dev-dashboard example failed at run time with `Function not found: env` even though its app.xml opts in via `features="file-io, system, science"`. Cause: the `nemo` binary depended on `nemo-extension` without the `pkg-env`/`pkg-sci`/`pkg-process` cargo features, so those packages were never compiled in — a package needs *both* the `<script features>` opt-in and the matching cargo feature. Added `pkg-env`/`pkg-sci`/`pkg-process`/`all-packages` features to the `nemo` crate that forward to `nemo-extension` (default = `pkg-env` + `pkg-sci`; `pkg-process` stays opt-in so a stock binary can't spawn subprocesses — compiling a package in never weakens the sandbox, since the per-script `features` attribute is the independent authorization gate), and a `warn!` in `register_standard_functions` when a script feature is requested but the cargo feature is absent (so the failure is diagnosable instead of a cryptic "Function not found"). Fixed both example READMEs to use `--app-config` (not `--config`, which is the TOML path) and the dev-dashboard to build with `--features all-packages`. Confirmed rhai-fs writes were never broken — the task-list persists `done`/`icon` changes to `examples/task-list/tasks.json` (git-ignored). Added `test_dev_dashboard_refresh_all_runtime`. Updated [extensions](/docs/knowledgebase/concepts/extensions.md).
* **Correction/Fix**: The persistent-scope seeding above is only a *partial* fix — it lets the **entry** function of a `call` see the seeded scope, but Rhai script functions are pure: a function invoked from another function (handler → helper) gets a fresh scope and cannot see any top-level `let` **or** `const`. The task-list and dev-dashboard example handlers relied on cross-function module state (`tasks_loaded`/`tasks_cache`, `samples`/`initialized`) and so still failed at run time (`Variable not found`), which is invisible to compilation since Rhai resolves names at call time. Rewrote both example scripts to keep **no** module state: shared constants are zero-arg functions, shared mutable state uses the host store (`get_data`/`set_data`) and the components themselves. Also fixed three latent bugs the module-state error had masked: `exists(path)` → the `.exists` getter, non-truncating `"w"` writes corrupting `tasks.json` (now `truncate_file()` first), and date-only `datetime_parse` (needs a full date-time). Added end-to-end mock-`PluginContext` tests (`test_task_list_handlers_end_to_end`, `test_dev_dashboard_stats_runtime`). Corrected [extensions](/docs/knowledgebase/concepts/extensions.md).
